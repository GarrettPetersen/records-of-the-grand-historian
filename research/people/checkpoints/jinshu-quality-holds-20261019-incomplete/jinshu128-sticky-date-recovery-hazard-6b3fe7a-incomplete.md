## Recovery provenance hazard

In staged `scripts/run-people-date-workflow.mjs` lines 132–152, startup takes the host process lock and then reconciles every same-worker, same-host non-ready claim for which the executor is not busy. It sets the claim to `ready` if the installed report is currently `audited` and the source/extraction fingerprints match (or satisfy the repair-receipt condition). The matching-report path does not verify that the audited report was produced by this particular retained generation or its jobs. `scripts/lib/people-date-audit.mjs` lines 172–184 verifies report structure, packet fingerprints and current references, but not which generation published it. Thus, if this worker is invoked while an unrelated matching audited report is installed, the current claim can be classified `ready` without generation-origin proof, even though this retained work is interrupted. This is a code-path risk, not a claim that it has already occurred or that the report's dates are wrong. The same runner's lines 174–180 archive a `ready` claim and create a fresh one when processing a subsequently eligible target, so an erroneous ready transition can affect recovery ownership. Preserve the existing claim and all retained artifacts pending a tested generation-aware fix.

## Existing hold guards and remaining race

The earlier suggestion that a pre-existing hold would simply be overwritten on normal restart was based on an older working-tree version and is **not established for this staged code**. At `scripts/lib/people-date-workflow.mjs` lines 441–472, `assertCompletedGenerationSafe` identifies a current `needs-revision` or `research-blocked` report and rejects an already-started retained audit such as this state. The runner calls that check in its reservation CAS at lines 167–168, and `runDateWorkflow` calls it again at lines 483–488. The latter captures the installed report fingerprint and checks it again immediately before recording at lines 562–567 and 585. If a hold is already installed before a normal restart, the guard blocks this retained state; if it changes during ordinary execution, the fingerprint check is intended to stop publication.

However, this does not prove that separately installing a host-written hold is safe right now. `recordDateAudit` in `scripts/lib/people-date-audit.mjs` lines 187–198 validates and archives the prior report before writing, but does not itself acquire the date-runner lock, check the queue claim, or atomically combine the report write with a queue transition. The process snapshot and absent lease are not a future-exclusion guarantee. A same-worker startup can race the report write and mark the active claim `ready` while the previous report is still audited; another writer could intervene between a report-fingerprint check and the final write. A hold written without coordinated host exclusion and provenance-aware queue reconciliation therefore cannot be asserted safe from these observations alone. The queue remains `active`, and merely writing the hold would not itself change or release it. Do not invoke such a write, claim takeover or lock deletion on this evidence. Reassess only under tested, coordinated recovery with current source, report, state and ledger fingerprints.
