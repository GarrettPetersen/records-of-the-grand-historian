## Release safety boundary

1. Treat the protected Git branch **commit tree**, not the live working directory or queue, as the publication snapshot. A reviewed PR's single tree must contain (a) the monotonic quarantine record, (b) the exact original report as immutable history if changed, and (c) any replacement report and source/extraction changes being published. The build and release verification must consume that exact merged tree. A complete tree exists or it does not; a process crash cannot expose a half-updated report and quarantine within one commit.
2. Enforce the quarantine as a mandatory tracked manifest; fail loudly if absent or malformed. A held entry gates its chapter regardless of whether the current report, source or extraction has changed. Permanent defective-report hashes survive resolution; deleting a record or restoring an old defective report must not turn a chapter into `audited`.
3. Make release an explicit, reviewed disposition *within the same manifest*, not deletion. It must bind the exact fresh independently approved replacement report bytes, its source and extraction packet hashes, review provenance, and independently verified source evidence. A resolved entry is accepted only if all pins match the actual tree and the normal complete date-report and current-reference validators succeed. Any mismatch, missing file, malformed resolution, stale source or previously quarantined report returns non-audited or fails. Identity and editorial gates remain separate. If the replacement is not yet approved, retain held state rather than synthesizing dates.
4. CI must compare the proposed merge tree against its protected base: reject deleted/rewritten quarantine history and unreviewed resolution changes, validate all pins and genuinely independent reviewer identity, and run scoped and required global validators. It must test the **merge result** or require an up-to-date branch. Do not use a branch/PR's old passing check as evidence for a different merged tree. Use normal required CI and protected-branch rules; no force push or bypass.
5. Stage with non-force compare-and-swap semantics: build a commit from the exact observed target parent, and use a normal fast-forward update which rejects a concurrently advanced ref. On rejection, inspect the new target, preserve all prior artifacts, rebase/recreate a candidate with exact new before-hashes, and rerun validation. Do not replace a changed report because an earlier snapshot matched. Master PR merge remains subject to required CI and the user's release policy.

## Cross-host worker coordination is a separate requirement

The Git snapshot boundary prevents half-published *release trees* but does not prevent a worker with an older checkout from writing local files or proposing an obsolete report later. An append-only tombstone plus merge-result gate prevents that obsolete report from becoming a published approval, provided every protected release enforces it. It does not prevent transient local writes, workers that ignore those checks, or force/bypass by an authorized administrator.

For robust future scheduling, add a shared-ledger, per-chapter quarantine/fence generation checked inside the same CAS that reserves a chapter and checked again at each **authoritative publication transition**. Hold creation must add a separate fence without deleting/replacing a sticky owner or its jobs. A retained owner may finish computing an isolated artifact, but it cannot publish against a different fence generation. A genuinely crash-safe implementation needs a durable publication receipt and a proven protocol joining the ledger fence to the Git tree; a lease token alone cannot fence an old writer after expiry if the downstream Git server does not enforce that token. Existing workers that do not implement this protocol must be allowed to finish naturally or be shown unable to publish before the fence is treated as effective. Do not infer that from an expired lease or a process-name scan.

The repository currently lacks this end-to-end fence and automatic hold resolution. For an immediate correction, limit action to reviewed immutable-tree publication with protected CI, while preserving live claims; explicitly label it a publication safeguard, not cross-host write exclusion. If the publication owner cannot prove the exact chapter's old worker is unable to publish through a bypass path, retain the quarantine and defer any canonical replacement that would race it. Unrelated chapters can continue.

## Required adversarial acceptance tests

- Missing/malformed/duplicate manifest; missing or malformed resolution; audited, un-audited, stale and deleted source/report; source/extraction changes while a hold exists.
- Original report restored after resolution; deletion of tombstone; unrelated later report; reused old reviewer; replaced evidence; crash before or after every durable phase. Never expose a false `audited` result.
- Two-host same-chapter concurrent scheduling, existing sticky owners, expired-but-still-running worker, holder crash, delayed old artifact, queue CAS retries, competing stale branch and replay after report change. Keep the original claim/jobs and artifacts, and disallow bypass through direct date repair, combined curation, scheduler release/takeover, progress, site catalog, and ebook generation/validation.
- Old passing CI versus advanced protected base; result-tree validation; fast-forward rejection without force. Confirm Git history retains the exact old report and that the resulting deployed catalog/progress is rebuilt from the merged tree. Local caches can be stale and are not evidence of deployment.

No result above establishes that a chapter is editorially closed, date-approved, identity-cleared, published, or complete. Only separately reviewed successful source-based audits and all normal downstream gates can establish those outcomes.
