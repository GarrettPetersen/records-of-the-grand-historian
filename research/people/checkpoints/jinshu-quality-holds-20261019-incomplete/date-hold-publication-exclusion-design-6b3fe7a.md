# Date-hold publication coordination: research design

This is a proposed design, not an implemented or authorized publication mechanism. Code references below are to staging commit `6b3fe7a8c4f5072b9fd44e5e74140d8a1fd88b17`, not necessarily the current dirty checkout.

## Observed behavior and gap

- `scripts/people-date-audit.mjs:27–29` calls `recordDateAudit` directly. `scripts/lib/people-date-audit.mjs:187–198` validates the packet, archives a parsed old report and atomically replaces the local report, but has no shared queue reservation, local host lock, or expected-old-report byte comparison.
- `scripts/run-people-date-workflow.mjs:132–134,158–181` uses one local host lock and queue-CAS reservation. The lock is not cross-host; `scripts/lib/process-run-lock.mjs:45–61` automatically unlinks an apparently dead lock by default, which is prohibited for the preserved lock. `failIfExists` fails safely but cannot acquire it.
- `scripts/lib/people-date-workflow.mjs:414–438,486–488,532,567–585` checks for report changes during workflow and uses the same recorder for direct and repair publication. Checking a hash and later replacing a file is not a cross-process atomic compare-and-swap.
- `scripts/lib/people-combined-curation.mjs:295–358` provides an existing useful model: exact prior claim, durable receipt, pending marker, checkpoints, lease renewal and validation. It is not a general exclusion fence for the legacy recorder or for independent Git checkouts. `scripts/lib/people-date-stale-reconciliation.mjs` can also move a report to history and must participate in any complete design.
- `scripts/lib/people-date-audit.mjs:172–184`, `scripts/compile-people-catalog.mjs:585,937` and `scripts/lib/ebook-current-date-audits.mjs:21–43` consume tracked source/report state, not the shared queue. A queue-only pending hold cannot itself block a stale build or change an already deployed site.

## Proposed minimum protocol

1. Use the existing remote queue CAS to install a durable, per-chapter publication transaction, with unique transaction ID, exact source/extraction fingerprints, prior and proposed report **byte** hashes (including explicit absence), owner/host, prior claim snapshot, and a content-addressed durable receipt. Create it only when no conflicting claim exists, or under the caller's exact existing worker generation and executor token. Preserve sticky claims, jobs, artifacts and leases; do not take over or release another worker's claim.
2. All claim acquisition, legacy recording, workflow direct/repair publication, stale-report archival, combined curation and other chapter writers must fail closed on a conflicting pending transaction and recheck ownership before publication. Drain old executors and prohibit older binaries before activating the rule: queue CAS cannot fence clients that do not observe it. Acquire the host lock without unlinking a pre-existing lock.
3. One designated publisher host or transactional service is the authority for actual publication. Under the transaction fence, persist the receipt and exact original bytes; verify current old bytes and all input fingerprints immediately before replacement; atomically replace, validate, checkpoint, and publish through normal staging with an expected-ref update and protected PR/CI. On retries, accept only exact old/new states. Preserve any third state and stop. A remote lease alone cannot prevent a partitioned, previously authorized process from writing after expiry: an authoritative serialized write/service or equivalent durable fencing is required, including for separate host checkouts and merges.
4. Complete the ledger transition only after verifying exact published output; pending work survives crashes and lease expiry until the same receipt is explicitly reconciled. Recovery must cover both report-only holds and multi-file repair publication; it must never infer ready from merely matching input hashes.
5. Required publication/CI checks must see the authoritative pending transaction or tracked equivalent and reject an unincorporated hold. Never depend on ignored host files or local locks on CI. A previously deployed master cannot change until a verified tracked hold is merged and deployed.

Offline tests should include competing queue CAS attempts; legacy CLI and each writer under a pending transaction; different generations with equal inputs; absent, formatting-changed, or unexpectedly replaced old report; crash/replay after every phase; expired and partitioned executors; foreign and sticky claims; combined-curation and stale-archive interactions; multi-file repair recovery; and current catalog, progress, ebook and protected-branch behavior. No test should use real claims or live locks.
