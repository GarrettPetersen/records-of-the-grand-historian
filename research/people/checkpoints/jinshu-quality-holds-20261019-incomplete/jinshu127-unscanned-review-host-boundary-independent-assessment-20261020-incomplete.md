# Independent assessment: host-controlled unscanned-name review

Research-only assessment of `jinshu127-reconcile-isolated-20261019/unscanned-review-independence-design-20261020-incomplete.md`, SHA-256 `88bdffbae923b5f2e3022170814e5d90443440ca24f3916289c6c8476297eeae`. No review receipt or production integration is implemented here. The proposed requirement for a fresh independent review is sound; hashes and self-declared reviewer IDs alone cannot establish that the required conversation happened.

## Concrete facilities already in this repository

- `scripts/sdk-people-editorial-review.mjs`, SHA-256 `dd71f2bc8c9304714606e64d2caf01af813fde81b0fece3c3cc4c0f501a1f5b8`: its sealed reviewer options and `Agent.create` create a cloud reviewer; the host sends the prompt, observes a run ID and completion, downloads the artifact, then **overwrites** the artifact's reviewer metadata with the actual SDK `agent.agentId` and result ID before normal decision validation. This is a concrete pattern to adapt, subject to existing authorized lane capacity, budgets and sticky recovery rules. Its host-state JSON is not by itself a cryptographic attestation.
- `scripts/lib/people-date-worker.mjs`, SHA-256 `714c35bfa7c91fd9151a624b4b77c55f1ed40b91a90e352f1c7ab1abd3e30a79`: cloud execution saves SDK-created agent/run IDs, resumes retained agents with `Agent.resume`, lists runs and downloads artifacts. Its separate attachment worker explicitly says an attachment's claimed identity is a human attestation, **not machine proof**; it must not be upgraded by merely copying its claimed string into a receipt.
- `scripts/sdk-inspect-run.mjs`, SHA-256 `27b82dcbcbe75a1ff5587f91a955fef6470e401e4db00a44036ebf1c54015c15`: `Agent.getRun` can inspect a cloud run; when the returned run supports conversation, the script reads its turns. This suggests an authenticated provider-side recovery check, but the code alone does not prove immutable retention, availability after expiration, or that a conversation includes every exact packet byte. Verify those properties for the actual SDK/provider before depending on them for durable proof.
- In the current Codex runtime, `collaboration.spawn_agent` creates a child agent and returns its runtime identity; direct messages and `list_agents` expose live task status. A host that actually creates a fresh reviewer and observes its result can preserve those events and the exact packet/decision hashes. A canonical task name or a JSON assertion supplied later by an arbitrary agent is not independently verifiable dispatch evidence. The listed tools do not establish a signed, durable event log for later offline consumers.

## Minimal safe integration and trust boundary

1. The trusted host freezes the exact source, extraction, candidate/reconciliation proposal, and full review-packet bytes and their hashes **before** reviewer creation. It records which live host operation authored or accepted the current proposal; do not fill historical null IDs with guesses. Runtime creation of a genuinely new, isolated reviewer after the proposal was sealed can establish this reviewer's separation from the proposal-writing conversation without requiring retroactive identities for old extraction or editorial sessions. Verify the provider's actual fresh-create semantics and keep any known conflicting current IDs excluded; a model label or a newly invented local name is not sufficient.
2. A host-owned dispatcher creates the reviewer through an actual supported runtime, sends the sealed packet (including all context necessary to judge the occurrence) and records the provider-issued agent/task ID and run ID returned by the runtime—not by the model's JSON. The worker may return decisions and source witnesses only. The dispatcher retrieves the artifact from that specific finished run, replaces self-reported identity with observed IDs, checks every decision, re-hashes all frozen inputs and result, and rejects missing/mismatched/stale bytes. No automatic self-approval, candidate-accounting shortcut, or date/identity bypass follows.
3. **Live acceptance boundary:** the same trusted host process that observed creation, send, finish and retrieval can verify these events in memory and perform the normal guarded handoff. This is host-process attestation under the repository's trusted-orchestrator convention, not cryptographic nonrepudiation. A callable library must not accept an arbitrary `independent: true` or JSON receipt as equivalent to the live observation. It must retain atomic publication, no-overwrite, sticky recovery, and all existing validation requirements.
4. **Restart/offline boundary:** a mutable JSON receipt plus a SHA-256 digest merely detects accidental changes if the expected digest is already trusted. If a worker/caller can write the same filesystem under the same OS account, it can fabricate both a receipt and its digest. A signing key or public-key file stored next to the receipt is not an independent trust anchor. For durable machine-verifiable replay, either authenticate and inspect a provider-side event/run/artifact binding with sufficient retention and exact-byte evidence, or use a signing service/key protected from reviewer access with a separately pinned verifier trust root. Scope by provider and account, include run and creation event, and test that a forged receipt, arbitrary reviewer, stale packet, truncated review, different proposal and artifact replacement all fail. If no such boundary can be verified after restart, hold the result for host-supported re-observation or an explicitly independent new review; do not silently trust a self-attested receipt or abandon sticky work.

The host process and collaborator agents here share the user's filesystem and may share the same OS identity; permission bits alone are not evidence of isolation against another same-user process. Cloud worker isolation and SDK authentication can narrow exposure, but must be verified rather than assumed. Neither this proposed design nor repository metadata proves the independent identity of legacy null-ID workers. It avoids making those absent fields a new mandatory gate while still requiring an actual separate source review and retaining all existing editorial, date-audit, identity and publication gates.
