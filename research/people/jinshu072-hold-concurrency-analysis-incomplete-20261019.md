# Date-hold concurrency analysis (not an implementation)

Baseline: remote staging `e29dc9e5cdda6f73f9709ef0778af2b47d3e2a37` and queue `4aca09929f40d88b55271e75e780d6423d494b2c`. Confirmed by `git ls-remote`; no queue mutation. The shared checkout differs from the staging tree, so the conclusions below were checked against staging blobs where material. This note and the parent prototype are ignored local research, not a production safeguard.

## Confirmed writers and hazard

* `scripts/people-date-audit.mjs` invokes `recordDateAudit` directly. In staging, `scripts/lib/people-date-audit.mjs` validates the incoming report, writes prior report history, then writes the new report. It does not acquire the runner's local lock or shared queue lease. Its `dateAuditStatus` reads only source, extraction and report, not an independent hold.
* `scripts/lib/people-date-workflow.mjs` publishes a date repair with separate receipt, extraction, and report writes; it also calls `recordDateAudit` for initial report results. `scripts/run-people-date-workflow.mjs` protects its own invocation with a local process lock and per-chapter ledger lease, but cannot make an unrelated writer honor either. Its startup reconciliation checks whether the installed report is audited before reserving work, so the old 072 approval may make the partial work appear ready before the finding is handled.
* `scripts/lib/people-combined-curation.mjs` uses a local process lock and obtains a lease with shared-queue CAS. It renews between file writes and checkpoints; this is not an atomic transaction across local files, the queue branch and a separately introduced hold. `publish-people-combined-curation.mjs` calls it. Running processes on distinct hosts have distinct local files and locks. Leases can expire and `--takeover` is intentionally an operator-controlled override, so a lease is not storage-enforced fencing for an old paused process.
* The dirty shared checkout has `scripts/reconcile-stale-people-date-workflow.mjs`, which calls `archiveStaleDateReport` and `archiveStaleDateWorkflow`, renaming local canonical report/workflow paths before the queue CAS. That entry point is absent from the inspected staging commit, so do not mistake it for deployed code. If deployed later, a precheck alone is not an exclusive transaction with the running publisher.
* `scripts/compile-people-catalog.mjs` derives per-chapter audit status through `dateAuditStatus`; `scripts/lib/ebook-people-readiness.mjs` consumes the catalog status. Status guarding alone only helps builds using the new code and complete hold data. `scripts/prepare-people-sparse-checkout.mjs` currently selects the report, extraction, repair and history paths, but not a future hold path. Existing sparse checkouts need explicit migration and verification, not just a modified preparation helper.
* Search found many `scripts/stage-*.mjs` and `scripts/curate-*.mjs` one-off writers. Most examined staging helpers write proposed candidates under `date-repairs`, not canonical audit reports; they are not proof of a complete writer inventory. Search and review remaining source/extraction/report writes, downstream generation, sync, and Git/PR publication paths before declaring universal enforcement.
* Staging's `.github/workflows/master-build-gate.yml` runs on the proposed master PR merge commit and invokes the full site build. It also runs `test-people-unresolved-hold.mjs`, whose fixture checks unresolved markers embedded in an extraction. It does not test or read the independent 072 hold proposed here. Branch protection and actual required-check configuration were not independently queried. Its full build compiles the catalog, which presently sees the old report as audited.

## Required publication design

1. Treat the validated Git revision consumed for staging/merge, not an independently mutable per-host checkout or a lease alone, as the authoritative publication boundary. A durable hold must be versioned alongside its affected chapter and be checked on the exact merged tree by a required CI gate before a deploy or ebook is treated as complete. A stale branch based before the hold must be updated/merged with it; the gate must reject missing, malformed, unresolved, stale or tampered holds/closures. The gate and its own CI configuration must be protected from stale changes. Verify actual branch protection and build workflow; do not assume CI currently runs a hold validator.
2. Make a hold an append-only, content-addressed finding with exact scope, affected item/evidence, cited report identity and current input fingerprints. Absence of the optional hold directory is not proof that an old sparse checkout has fetched it: a versioned manifest or required schema marker and deterministic scope selection should make a missing manifest/entry fail closed. Migration must first establish a consistent baseline and validate sparse selections. Closure must be separately reviewed, bound to the hold hash, new full independent report and current input fingerprints; changing/reordering the extraction must not silently clear the finding. Reviewer identity and source relevance require real independent human/model review beyond structural checks.
3. At the host level, all cooperating creation, closure, report recording, repair and combined publication paths need the same local lock and shared claim/lease ownership. Acquire before reading state, renew and verify ownership immediately before operations, preserve sticky owners and recovery artifacts, and provide crash/replay receipts. Disable or route direct `record` and stale-reconcile paths through that protocol. This reduces in-host races, but is not itself storage-level fencing: a sleeping old process can act after its lease is stolen/expired. Never claim it solves split brain.
4. Reject commits at final authoritative publication unless the source, extraction, report, hold, closure and approved receipts are checked together on the resulting commit tree. Atomic Git commit/ref compare-and-swap serializes competing accepted tree updates; ordinary checked-out multi-file writes are not atomic. A multi-file receipt can recover host crashes, but readers must never mark its intermediate state as complete. Ensure PR merge methods, staging host exact-file commits, background workers and site builds all use this same gate, including delayed old worker results.
5. Rollout requires a quiescent or explicitly drained old-executor window. Confirm no live process or live lease first without deleting or taking over either; verify preexisting sticky assignments remain owned. Publish the hold and gate in one coherent reviewed change, migrate active sparse clients, and only then resume an existing owner with preserved jobs. Old binaries/old source revisions must be rejected at the authoritative gate, not trusted to observe new code.

## Minimum adversarial tests before deployment

Run separate-process and isolated simulated-host tests, not only preflight unit tests: hold creation concurrent with report overwrite; hold creation concurrent with repair and each combined-publication checkpoint; lease expiry followed by an old worker waking and attempting publication; CAS conflict between simultaneous Git updates; merge of an old branch after a hold arrives; stale sparse checkout without the hold manifest; stale-reconciliation races; crash after every durable write; malformed/tampered/removed hold or closure; report, source or extraction changes and reordered item IDs; offline and network-failure conditions; and ebook/catalog behavior from the exact accepted tree. Test direct CLI writers as well as the orchestrator. Preserve fixtures and evidence.

No implementation is supplied: the present prototype has acknowledged race and migration gaps, no coordinated hold-authoring protocol, and no required final-tree gate. It is not safe to stage as a fix. No active process, lock, queue claim, recovery artifact, canonical data or Git index was changed in this analysis.
