# Completion-first people glossary process

This is the current orchestration policy.

The November15 throughput objective is50completed, live-published chapters/day.
Follow `PEOPLE_THROUGHPUT_TARGET.md` for measured4→8→12remote admission, bounded
bundled person evidence, completion-first scheduling and batched releases. This is
a target requiring real measured releases, not a promise or permission to weaken gates.

Follow `PEOPLE_CHAPTER_COMPLETION_RULES.md` to close source-supported records without
open-ended optional research. Reviewed uncertainty is a valid native outcome;
contradictions, unsupported asserted facts and known fixable English defects remain
blocking. Host-built packets and incremental editorial history prevent report formats
from forcing redundant model passes. Existing holds require explicit reconciliation.

**November 15 simplification and synchronization:** all chapters follow
`PEOPLE_CHAPTER_OWNER_PROCESS.md` at any level of completeness: one complete owner submission and one complete
independent final review, including canonical identity evidence. Extra native report
formats are host serialization, not extra review layers. Supply all existing partial
work and valid independent proofs to the same owner; complete only missing/affected
work without resetting the chapter or its holds. Follow
`PEOPLE_MASTER_SYNC.md` at startup and release/dispatch boundaries; a dirty checkout
or alternate-index release never excuses an obsolete shared baseline.

**November 13 chapter-owner design:** adopt `PEOPLE_SINGLE_OWNER_WORKFLOW.md` at
the next idle boundary: one persistent capable chapter agent, bounded public-history
lookup (`PEOPLE_LOOKUP_API.md`), one independent final reviewer, then dependency-scoped
patches where native proof composition supports them. Preserve running ownership
and every native approval/publication gate. The lookup service is retrieval only;
its installation does not enable general approval reuse across source edits.

**October 30, 2026 user-authorized process revision:** chapter completion uses
bounded canonical-person dossier reviews, not exhaustive O(k²) same-name pair
comparisons. This explicitly supersedes the old zero-touching-pairs completion
condition. Adoption still requires integrated code, independent review, passing
CI and a real nonempty live chapter receipt; this text alone grants no approval. It supersedes extraction-volume targets,
old deadline wave recipes, and waiting for 25–50 new extractions before identity work.
Existing source, editorial, chronology, identity and publication gates remain intact.
A planning checkpoint grants no approval.

## Operational changes after the November 6 process audit

These are scheduling and evidence requirements, not a new approval format, a reason
to repeat unchanged reviews, or permission to change an active invocation's inputs.
Adopt them at its next idle boundary. The replacement campaign objective is in
`PEOPLE_GLOSSARY_ORCHESTRATOR_GOAL.md`; it does not itself change the app's saved goal.

### Close the English/source pass before commissioning downstream work

Distinguish **proposal queue empty** from **full source/editorial coverage verified**.
Before a new complete date audit or identity wave, record who reviewed the complete
chapter, its pinned source/English inputs, the covered unit IDs and both English
fields where present, and the accepted/rejected/applied repair evidence. Check source
propositions, kinship, event ownership, names/titles, omissions, repeated uses and the
parallel English field. Existing review evidence may satisfy this; do not commission
a duplicate full review merely to generate another receipt. Reuse unchanged unit
proofs only through the normal verified provenance path; do not manually retag hashes.
If full coverage cannot be established, call editorial status **unverified**, not
closed. Split large source passes into bounded source-complete parts and aggregate
their exact coverage, with no dropped units or invented approvals.

Collect corrections across that source pass, independently review worker-authored
replacements, and apply one coherent chapter batch before freezing downstream input.
Do not alternate a new complete date audit with one-at-a-time English corrections.
When an active review discovers English defects, preserve its actual result and let
started work drain safely. Keep supplemental repairs outside closed date/identity
schemas. Resolve/apply the chapter repair batch before commissioning another full
review. Genuine later errors must still be fixed; freezing is not permission to hide
them. Inspect why the prior source pass missed them instead of repeating the same
unchanged prompt. Review only affected work where the native validators support it;
otherwise retain the required full independent audit.

### Separate routine content review from application-code development

Use the existing reviewed production appliers and sealed before/after data contracts.
Routine unchanged code does not need a fresh model code review for each chapter;
repair content still needs independent review and all native acceptance checks.
Do not create a bespoke applier/framework for each packet. If the supported path
cannot represent a legitimate change, record the exact gap, fix the shared production
path once with preservation regressions and independent code review, then reuse it.
Do not extend an interface or duplicate implementation just to work around a hold.
Preserve unnamed people, Chinese evidence, existing claims and identity assignments
on English-only edits; tests must cover those invariants as well as intended changes.
New/mutated code still needs review. Never suppress a real validator failure to save
time or treat a helper's successful execution as independent content approval.

### Count the whole chapter cost, not just each invocation

Extend the existing chapter work order, not a new competing ledger, with cumulative
review/repair invocations, full-audit passes, source generations, known raw model
usage/cost, elapsed time, late editorial defects and reusable accepted results. Mark
missing provider usage unknown, not zero; distinguish raw model value from billed
charges. Preserve that accounting across worker/chat changes and source reconciliation.
Use the existing three-round date breaker. Source edits and manual/focused paths do
not automatically authorize more spending. After either two completed full audits
without chapter approval or two successive downstream passes discovering missed
editorial defects, stop new *full* audits and diagnose the source/method/application
gap. Preserve independently reviewed focused research and active jobs; a new complete
audit requires a recorded changed approach, independently reviewed corrective evidence
and a bounded next-run budget under the existing authorization. Do not invent a dollar
limit unrelated to measured work or silently raise the existing cost/round limits.
This accounting policy is host-enforced until integrated into the native scheduler;
do not claim the current per-run breaker enforces cumulative chapter spending.

### Remote generation and storage reuse (November 18)

Follow `LOCAL_DISK_STRATEGY.md#preventing-duplicate-storage`. Local corpus catalog,
site-index and full registry builds are disabled. Submit exact reviewed source/code
through normal remote PR CI; use its compact native qualification receipts and
the exact Cloudflare deployment/live checks. A failure of an old local generated
catalog does not require another chapter source review. Preserve accepted source
and canonical proofs, and fix the output writer remotely without increasing local
heap or allocating another registry. KDP exports remain separate private artifacts.
Use the source-only checkpoint helper, bounded native deltas and pinned lookups.
The frozen local registry inventory protects retained proofs and blocks new copies;
do not expand it to bypass the rule. No broad recovery directory snapshots.

### Keep a short, explicit completion frontier

Keep one primary completion target and at most two other active completion chapters.
For each, show owner, current pins, full-source coverage state, date/identity status,
exact next deliverable and concrete holds. Historical recovery directories are not
automatically active WIP. Park a genuine research hold explicitly; do not repeatedly
poll or rewrite it, and do not discard it. Select the next eligible target from this
frontier after inspecting its evidence, rather than repeatedly assuming legacy positive
date reports mean the chapter is ready. Qualified or merely fingerprint-current reports
known to be contested must be reported separately from uncontested approvals.

Every bounded handoff reports **newly published chapters**, **data-qualified chapters**,
**applied reviewed corrections**, **known holds**, and **code-only work** separately.
A successful code release is not chapter throughput. A real new finding is useful
work, but it does not establish convergence. Keep fresh-chat/60-minute boundaries:
another turn in the same oversized conversation is not a fresh chat. Check resources
before each dispatch. Use the default disk reserve for local work and the
[GitHub-only preflight](LOCAL_DISK_STRATEGY.md#cursor-cloud-coordination-through-github)
for eligible Cursor Cloud campaigns.


## Repair English omissions when found

A definite English omission or mistranslation requires a concrete complete replacement,
not only a flag or an outside-scope note. Check both English fields and repeated uses.
Supply supplemental repairs in an artifact with book, chapter, unit ID, field, exact
before/after text and source-based reason; keep them separate from closed-schema date
or identity reports. The host routes these into the active editorial application work,
with a separate reviewer for worker-authored repairs. Preserve independent review and
normal extraction, chronology, identity, CI and publication gates. Do not defer known
fixable English to a future corpus-wide pass. An empty proposal queue alone does not
prove every source proposition has been translated.

## Bounded chapter work order

1. Finish source/editorial corrections first: paired translations, repeated names and
   transcription. Run current extraction/editorial gates. Repair the existing extraction;
   re-extract only for a demonstrated defect that requires it.
2. Obtain current independent date approval. Genuinely undated facts stay undated;
   actual ambiguity stays on research hold. Follow the date loop breaker, not repeated
   whole-chapter reviews of unchanged candidates.
3. Pin the actual source, extraction, editorial history and date-report bytes. Record
   a small work order under `data/people/generated/completion/BOOK/NNN/`, not a checkout.
   Keep the original evidence in place; a fingerprint is not permission to rewrite it.
4. Reuse the current immutable canonical-person dossier registry. Build/update it
   once from validated source records and accepted membership decisions, never once
   per review packet. One logical dossier represents one accepted canonical person;
   chapter records remain its cited provenance. Historical merge, separation and
   reviewed-ambiguity decisions remain valid constraints, not a new all-pairs queue.
5. Prepare one case per canonical person occurring in this chapter, covering every
   chapter-local record exactly once. Retrieve at most eight other dossiers per
   case through the name/alias index, with at most sixteen keys and eight posting
   reads per key. Record full posting counts/fingerprints, every omitted key and
   every overflow. Retrieval limits are admission limits, never proof of uniqueness
   or permission to discard a plausible match. No complete same-name pair graph,
   connected-component completion, or recursive external-chapter completion.
6. Independently review each case's source-backed retained identity assignment and
   exact cited Chinese evidence. The reviewer must confirm that the record denotes
   an actual individual, its chapter mentions belong to that record, and the accepted
   canonical membership is supported. An unresolved cross-chapter equivalence may
   finish as explicit reviewed uncertainty while records remain separate. It must
   not create a confident separation, a guessed match, or a new merge. A suspected
   false existing merge, unsupported chapter-person attribution, or conflicting
   primary evidence remains a concrete case hold. New merges still use the existing
   independently reviewed resolution-application gates.
7. Once every chapter-local person has current independent case coverage and no
   concrete case hold, run actual scoped website qualification/projection. A legacy
   same-name candidate count is not the chapter's release gate. Publication must
   preserve reviewed cross-chapter uncertainty visibly and reconstruct facts only
   from qualified source members. Source/extraction/editorial/date, unsupported
   family-target, source-fidelity, quote/artifact, CI and live-content gates remain.
   Do not use preview flags or change stale approval hashes to obtain a green result.

Freezing inputs means no speculative cleanup during downstream review, not ignoring
factual errors. Independently review genuine corrections, preserve the old generation,
reconcile affected work, and obtain fresh affected approvals. Do not change hashes to
keep approvals. Keep unrelated extraction changes out of the pilot acceptance release.

## Historical pair checkpoints and spending stops

The following retained command compares historical pair-frontier receipts. It is
diagnostic recovery tooling; its pair count is no longer a release gate or a model
worklist. New dossier checkpoints report person cases, approved/held cases, reviewed
uncertainty, source input pins, reviewer receipts and publication evidence.

Compare two historical compact checkpoints with:

```sh
npm run people:completion:check -- --baseline /absolute/baseline.json --current /absolute/current.json
```

Each JSON contains `scope: {book, chapter}`, chapter-local extracted `personCount`, `inputs` containing
SHA-256 byte digests for `source`, `extraction`, `editorial`, `dateAudit`, and
`unresolvedPairs`, an array of distinct two-element canonical-ID pairs. Derive pairs
from the current validated graph, not model estimates/raw block counts. Record graph
revision/generation and accepted decision receipts beside each checkpoint. Hash file
bytes, not paths. Do not substitute checkpoints for sealed evidence.

The command is read-only and diagnostic: it does not validate decisions, graph
freshness, date reports or publication. Input/people-count drift or added pair IDs
returns `replan-required` and nonzero exit. Zero pairs means `ready-for-release-checks`,
never `complete`. Zero-person checkpoints return `empty-scope` with nonzero exit;
they cannot satisfy the nonempty pilot. Malformed
checkpoints fail loudly. Preserve sequential checkpoints to expose reversals.

Date work permits at most three automatic repair/re-audit rounds and stops earlier
for repeated candidates or two non-improving rounds (`PEOPLE_DATE_AUDIT.md`). For
identity work, repeated unchanged case/evidence fingerprints require diagnosis
before another model turn. Reuse unchanged independent case proofs; reconcile
source edits and accepted membership changes explicitly. Do not
delete state, release sticky work, raise limits or change worker IDs to bypass a hold.
Continue another bounded chapter if useful work cannot proceed. A hold is neither a
completion nor a campaign-wide stop.

## What counts as done

Report these separately:

- Extracted/repaired: intermediate work, not glossary completion.
- Data-qualified nonempty chapter: current source/editorial/date/identity gates pass.
- Verified zero-person chapter: reviewed extraction contains no people; no pages
  expected. This does not prove the nonempty pipeline. Genre alone does not prove
  absence of people: check source review and candidate coverage.
- Published nonempty chapter: qualified output merged/deployed, generated person
  pages, both-language chapter links, inverse snippets, search and sitemap targets
  pass site verifiers and live HTTP/content checks for that deployment.

The first acceptance receipt must identify the chapter, nonzero published people,
exact source/approval/identity inputs, merged revision, successful deployment,
generated verification results and live checked person/chapter/search/sitemap URLs.
Check multiple mentions, shared names and inverse links; a 200 fallback page does
not pass. Check slug redirects where applicable. Changed inputs invalidate a stale
receipt. Synthetic fixtures are regression tests, not this production receipt.

Do not report published completion from claims, unit tests, PRs, audit approval,
build success alone or an empty extraction. Do not wait for 30 other chapters before
releasing the first nonempty acceptance slice: this is an exception to batch-size
targets, not to CI/master rules. Use exact reviewed changes and the normal PR path.

## Scale only the demonstrated path

### Crash-recovery operating profile (October 26, 2026)

The last crash was preceded by measured Codex backend allocations of about 79 GiB
and roughly 55 GiB swapped out; free disk subsequently fell below 1 GiB. A local
graph pass peaked around 2.4 GiB of JavaScript heap. These observations identify a
backend memory problem as a major contributor; they do not establish its software
cause. Do not assume free disk, cloud inference, compaction or simply reopening the
same long chat fixes it.

Use this conservative profile until successful small runs justify changes:

This host-safety profile overrides historical lane-filling and concurrency targets.
Let already-running assignments drain; retained or ready claims are not permission
to launch more work and must not be released merely to reduce concurrency.

- Use a fresh coordination chat with only a compact work-order handoff and exact
  evidence/receipt paths. Do not fork this campaign's accumulated history. End at
  the first bounded batch checkpoint or 60 minutes, whichever comes first; preserve
  a handoff before rotating. This is a session boundary, not permission to discard
  work, abandon sticky conversations or weaken any acceptance gate.
- Do not resume an unbounded automatic goal loop in the old chat. This crash-policy
  repair is the final task here; glossary production resumes from the saved handoff
  in a fresh chat. Do not create a recurring automation as a workaround.
- Initially use no parallel native Codex subagents. Follow
  `PEOPLE_REMOTE_CONCURRENCY.md` for the November 15 user-authorized staged remote
  increase. Separate chapter owners/reviewers can run concurrently across chapters;
  the same candidate must have one writer and a frozen independent review boundary.
  Keep bounded sealed evidence rather than inherited campaign history. This does
  not authorize a new broad extraction wave or bypass resource/publication gates.
- Run only one local heavy job at a time. Do not overlap full graph compilation,
  site/ebook builds, Git packing, or large packet construction. Use a 3 GiB Node
  old-space ceiling for newly launched heavy Node jobs; this limits JavaScript heap,
  not native buffers or total RSS. If it fails, preserve the partial run and change
  the batching/streaming approach rather than repeatedly raising the ceiling.
- Run `npm run people:disk:check` before each new dispatch/heavy job, after a job,
  and at least every 60 seconds while observing active work. On macOS it checks disk,
  system swap, Codex backend resident memory and OS memory pressure. Keep 30 GiB
  free; warn at 4 GiB swap and inspect consumers and growth before increasing
  concurrency. Stop new work at 8 GiB swap, 4 GiB combined Codex backend RSS, or warning/
  critical memory pressure. Unknown/failed measurements fail closed. Other platforms
  explicitly report this macOS memory check as not applicable, not as verified safe.
- These are admission checks, not a continuous watchdog or an application memory
  limit. On a breach, stop new dispatches and checkpoint compact state. Preserve
  current job IDs and verify actual remote/process state before resuming. Perform
  the active remediation procedure below; if the guard still fails after safe
  cleanup, record the remaining concrete action and any required user decision
  before ending the coordination turn. Never auto-kill the user's Codex/browser, delete
  swap, clear history, remove locks or discard recovery. If growth continues, ask
  about an app restart after preserving active work; a repository script cannot
  safely repair its allocator.
- Bound tool output: normally return at most 1,000 tokens, at most 4,000 for a
  necessary code review. Save large logs/results to their existing job artifacts;
  return counts, hashes and paths. Project search/connector responses before printing
  them. Never dump a corpus, entire API response, huge diff, or long conversation.
- Recover known cloud agents by stable ID. Scan historical agents only for an
  actual missing-ID recovery, not every poll or fresh assignment. Save agent/run IDs,
  usage and output paths as soon as available. Reuse sealed graph/results on unchanged
  inputs; refresh once per reviewed data/semantic change, not per polling turn.

Do not claim this repairs a Codex backend leak or guarantees crash prevention.
It limits exposure and stops new work well before the previously observed failure.
Keep the existing shared date-audit pool, worker IDs, packet ceilings, validation,
review independence and publication gates; do not introduce competing executors.

#### Standard memory-warning preview cleanup (October 31, 2026)

The user has authorized this bounded cleanup without repeated approval:

A warning starts active memory remediation. Stopping production is the admission
response; it does not finish the remediation task. Diagnose the largest relevant
physical footprints, verify ownership and perform the safe cleanup already
authorized. If the remaining useful action would interrupt active or uncertain
work, present the exact target, measured footprint, expected interruption and
restart plan, then ask once for the missing authorization or ownership information.
Keep that decision pending without assuming approval. Do not spend successive
turns merely repeating the same failed guard. If no safe action is available,
record the concrete external change needed and preserve the resource hold.

After cleanup or an external resource change, remeasure pressure, swap and the
resource guard. An actual passing measurement clears the resource admission hold;
record the new evidence and reconcile stale local hold summaries without changing
chapter approvals or automatically resuming a paused/blocked goal. Do not attribute
recovery to an action that was not performed or whose effect was not measured.

1. Pause new heavy work. Inspect OS memory pressure, swap growth and process
   physical footprint, including compressed/graphics allocations. Backend RSS
   alone can miss a large application GPU helper footprint.
2. Identify idle, superseded local development/preview servers. Immediately before
   signaling, verify the PID, executable/command, project working directory and
   listening port; check for connected clients and active task ownership. No
   connected clients alone is insufficient. Confirm a newer retained preview
   serves that project, or that the owning task has completed.
3. Save the exact restart command and checks in a private local cleanup receipt.
   Send SIGTERM only to verified idle servers. Keep the current/newest preview,
   active model/build/review jobs, MCP services and unknown services running. Ask
   before interrupting anything active or uncertain; do not escalate to force-kill.
4. Verify released ports and the retained preview, then rerun
   `npm run people:disk:check`. Resume heavy work only after an actual passing
   measurement, with the existing before/after/60-second checks. Preserve all
   claims, locks, recovery and history; keep every existing safety threshold.

### Oversized identity evidence and aggregate extraction authors

Keep the complete source packet and the full plan. Oversized transports split by
case ownership within the existing byte ceiling. Each part includes the complete
target chapter and every cited claim and mention unit for its people and anchors.
Preserve each actual report, producer and sealed part hash. Assign new unreviewed
parts to independent conversations rather than accumulating every part in one
context; keep the one-active-cloud-assignment resource profile. Recover an existing
part's producer and saved result before replacing work. All owned cases must assemble
exactly once, and every actual part producer must be independent of every extractor.
The aggregate names a real contributing reviewer and retains the producer of each
case. Then run the normal full-plan identity validator and publication gates. No
part itself certifies a chapter. Single cases that exceed the bound stay held.

Fresh preparation defaults to 256 KiB parts. Its receipt pins `transportPolicy`
(`schemaVersion: 1`, `maxBytes`) within the 768 KiB absolute ceiling. Run the read-only
`validatePreparedIdentityReviewArtifacts` preflight before model dispatch, and copy
that exact policy into the captured part journal. Recording reproduces the pinned
layout rather than applying a later default. A retained journal without this policy
requires explicit host reconciliation against its original preparation/invocation
and byte-identical parts; preserve the original journal and provider reports. Never
guess a policy, silently fall back, or retag a report to fit a new layout. Completed
identity proofs keep their normal unchanged-source revalidation path. A smaller part
limit alone does not prove lower compaction, cost or one-hour throughput.

Chunked extractions identify their actual contributing agents through `run.chunks`.
Exclude every actual chunk author from independent review; never invent an aggregate
agent ID or accept missing chunk provenance.

The normal identity recorder also accepts captured part journals. It re-derives
bounded transports from the exact full source packet, verifies each actual
producer/run and raw report hash, and rejects any aggregate that differs from
those reports. Published proof receipts retain per-part case fingerprints and
producer metadata. Pinned recording re-proves the registry input equivalence and
uses the primary checkout's shared identity lock/recovery directory; it still runs
the normal complete certificate validator. Runtime code is checked at its actual
module location, separately from configured data/configuration roots.
